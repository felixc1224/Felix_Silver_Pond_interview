**The architecture, layer by layer** (the page has the pictures; this is the one-paragraph version)

Input `3×32×32` → **conv1** (16 stencils of 3×3, padding 1) `16×32×32` → **relu1** → **pool1** (2×2 max) `16×16×16` → **conv2** (32 stencils of 3×3×16) `32×16×16` → **relu2** → **pool2** `32×8×8` → **flatten** `2048` → **fc1** `128` → **relu3** → **dropout** (off) → **fc2** `10` scores → softmax to probabilities. 268,650 parameters, and the page's bottom table shows that 97.6% of them sit in `fc1` — that's the reason bigger CNNs replace the FC head with global pooling, which we can discuss when we go to option 1.

**Hyperparameters (all in `baseline.yaml`) and what each one does**

- `seed 42` — fixes weight initialisation and shuffling so a run is repeatable. Not the split seed; that's frozen in the CSVs.
- `batch_size 128` — images per gradient step. Larger = smoother gradient, fewer steps, more RAM.
- `normalize true` — subtract per-channel mean, divide by std, so inputs are centred around 0. Makes optimisation much better behaved. This is the change that will break the `[0,1]` assert in `verify_data.py`, as flagged.
- `random_crop_pad 4`, `horizontal_flip true` — augmentation, train only. Each epoch the model sees slightly shifted/mirrored versions, so it can't memorise pixel positions. Typically worth +3–5% on CIFAR.
- `conv_channels [16, 32]`, `fc_hidden 128` — model width. More channels = more patterns detectable = more params and time.
- `dropout 0.0` — off for the first run so we see raw behaviour; turn to 0.25–0.5 if val accuracy lags train (overfitting).
- `epochs 15` — full passes over the 45k training images. Tiny CNN should plateau around 10–15.
- `optimizer sgd`, `lr 0.05`, `momentum 0.9` — SGD with momentum is the CIFAR classic. `lr` is the step size: too high diverges, too low crawls. Momentum keeps velocity in a consistent direction. Alternative: Adam at lr 1e-3, easier to tune, slightly worse final accuracy on CNNs.
- `weight_decay 5e-4` — a small penalty on large weights (L2); a mild regulariser.
- `scheduler cosine` — the learning rate glides from 0.05 down to ~0 over the run. Big steps early, fine steps late. Alternative: step (drop ×10 at fixed epochs) or none.
- `early_stopping_patience 5` — stop if val accuracy hasn't improved for 5 epochs; always keep the best checkpoint.

**Evaluation methods we'll use to judge it**

- *Learning curves* — train loss and val loss/accuracy per epoch on one plot. The shape is the diagnosis: both falling together = learning; train falling while val rises = overfitting; both flat and high = underfitting or lr wrong.
- *Confusion matrix* — 10×10 grid of true class vs predicted class on val. The diagonal is correct; off-diagonal cells show *which* mistakes: cat↔dog and automobile↔truck are the classic CIFAR confusions.
- *Per-class accuracy / precision / recall / F1* — overall accuracy hides that a model can be great on ships and terrible on birds.
- *Top-k accuracy* (top-2) — was the right answer at least second? Useful for "nearly right".
- *Calibration* — when the model says 90% confident, is it right 90% of the time? A reliability diagram shows this; cheap to add.
- *Worst-mistake gallery* — the val images it got wrong with the highest confidence. The most instructive plot there is, and matches your "see it with my eyes" style.
- *Final test-set accuracy* — run exactly once, at the end, on the sealed 10k.

## Claude

Think of `baseline.yaml` as the recipe card pinned above the stove. The code is the kitchen; the card says how much of what, and at what temperature. Change the card, not the kitchen.

**Why a file at all, and why YAML.** The alternative is hard-coding numbers inside `train.py` or passing twenty command-line flags. A config file means every run is fully described by one small text file you can commit, diff and copy: `baseline.yaml` → `exp02_dropout.yaml` with one line changed is a complete, reproducible experiment record. YAML specifically because it's readable by humans (indentation, no braces), supports comments, and `yaml.safe_load` turns it into a plain Python dict in one line. The alternatives — JSON (no comments), or Python dataclasses (more type-safety, more boilerplate) — are fine too; YAML is the ML convention.

**The five sections**, each matching one part of the pipeline:

`experiment` / `seed` — the run's name (used for the log and checkpoint filenames) and the randomness seed for weights and shuffling. Note the comment: this is *not* the split seed, which lives in `dataset.py` and is frozen in the CSVs. Two seeds on purpose: you can try a different initialisation without the validation set moving under you.

`data:` — the knobs `build_dataloaders` will read: batch size, workers, and the two transform switches. `normalize` and `augment` are here rather than in the model section because they're about how inputs are prepared, not what the network is. `random_crop_pad: 0` is the off-switch; `horizontal_flip: false` likewise — so an "ablation" (does augmentation help?) is two edits.

`model:` — `name` picks the class from the `MODELS` registry in `model.py`; everything else under it is passed straight into that class's constructor as keyword arguments (`TinyCNN(conv_channels=[16, 32], fc_hidden=128, dropout=0.0)`). That's the trick that makes option 1 later a one-line swap: add `vgg_small` to the registry, change `name`.

`train:` — the optimisation recipe: how many epochs, which optimiser and its learning rate / momentum / weight decay, which LR schedule, and when to give up. The comment on `lr` is a reminder that SGD and Adam want learning rates ~50× apart — the single most common "why won't it train" mistake.

`paths:` — where outputs land, relative to the repo root, matching your folder template: weights to `outputs/models`, CSV logs to `outputs/logs`, plots to `data/output`.

**Two things to know for the review.** First, nothing reads this file yet except `visualize_layers.py` (for `seed` and `model`); `train.py` will be the real consumer, so the field names here are a contract I'll have to honour there. Second, YAML's `5.0e-4` must be written with the decimal point and sign — bare `5e-4` is parsed as a *string* by YAML 1.1, a classic silent bug; that's why it looks slightly odd.

```python
import torch

```

**The docstring.** It's the same table `python -m src.model` printed, written by hand *before* the code, as the specification. The point of keeping it in the file: when you open `model.py` in six months, the first thing you see is the shape story, not the code. Two conventions in it: "batch dimension omitted" means every real tensor has an extra first axis for the batch (`[128, 3, 32, 32]`), which the table leaves out because it never changes; and "logits" is the standard word for the raw 10 scores before softmax.

**The design choice line is the one to remember.** A 3×3 convolution with no padding shrinks the image by 2 pixels (32→30), because the stencil can't centre on the edge pixels. `padding=1` adds a one-pixel border of zeros so the stencil *can* centre on every pixel and the output stays 32×32. The alternative — the classic LeNet/PyTorch-tutorial net — uses 5×5 convs with no padding, and the sizes go 32→28→14→10→5, which is correct but hard to narrate. With padding, only the two pools change the size: 32→16→8. Rule of thumb: *convs change the channel count, pools change the spatial size.*

**The imports.** `from __future__ import annotations` makes type hints lazy strings, so `tuple[np.ndarray, ...]`-style hints work on older Pythons and don't cost anything at runtime — purely a compatibility nicety. `OrderedDict` is what lets us *name* the layers inside `nn.Sequential` (`conv1`, `relu1`, …) instead of PyTorch's default `0`, `1`, `2`; those names are what the page and the layer table key on. Plain `dict` is ordered too in modern Python, but `nn.Sequential` specifically accepts an `OrderedDict`, so that's the documented form. `torch.nn as nn` is the module of building blocks: `Conv2d`, `Linear`, `ReLU`, and the `Module` base class.

Now `build_model`. It's a tiny *factory*: give it the config, get back a ready model. Four lines, each doing one thing.

`m = dict(cfg["model"])` — take the `model:` section of the YAML, which arrived as `{"name": "tiny_cnn", "conv_channels": [16, 32], "fc_hidden": 128, "dropout": 0.0}`, and make a *copy*. The copy matters because the next line removes a key, and we don't want to silently mutate the config dict that the caller still holds (they may want to save it alongside the checkpoint later).

`name = m.pop("name")` — pull `"tiny_cnn"` out and delete it from the copy. After this, `m` holds *only* the constructor arguments: `{"conv_channels": [16, 32], "fc_hidden": 128, "dropout": 0.0}`.

`if name not in MODELS: raise ValueError(...)` — `MODELS` is the registry dict a few lines above: `{"tiny_cnn": TinyCNN}`. If the YAML names a model that isn't registered (a typo, or a future `vgg_small` we haven't written), fail immediately with a message that lists the valid choices. Without this line you'd get a `KeyError: 'vgg_smal'` with no hint.

`return MODELS[name](**m)` — look up the class and call it with the remaining settings unpacked as keyword arguments. `**m` is the "spread" operator for dicts: `TinyCNN(**m)` is exactly `TinyCNN(conv_channels=[16, 32], fc_hidden=128, dropout=0.0)`.

**Why this shape rather than `TinyCNN()` directly in `train.py`:** two reasons. First, the YAML is the only place that decides which model and how wide — `train.py` never needs to know a class name, so swapping to option 1 later is a registry entry plus one line in the config. Second, the YAML keys and the constructor's parameter names are *forced* to match: if you write `fc_hiden: 128` in the config, `**m` raises `TypeError: unexpected keyword argument 'fc_hiden'` at startup rather than silently using a default. That's a feature.

**Alternatives:** a chain of `if name == "tiny_cnn": ... elif ...` does the same with more lines and no automatic error listing; a library like Hydra or `timm.create_model` does it with far more machinery than a two-model project needs. The registry dict is the lightweight middle.

**Break-it experiments:** change `name` in the YAML to `tiny_cn` → should list the valid names; add `fc_hiden: 64` → should fail with the unexpected-keyword error; change `conv_channels` to `[8, 16]` → `python -m src.model` should show the new shapes and a much smaller param count (the fc1 row drops to 1024×128).

Three roles in one picture:

```
baseline.yaml  ──(yaml.safe_load)──▶  cfg dict  ──(build_model)──▶  TinyCNN object
   text file                          just data                    a working network
```

`yaml.safe_load` is the part that reads the file and lets you see what's in it — that happens in the script, before `build_model` is called. `build_model` then takes that dict and *constructs* the model from it: picks the right class by name, feeds it the width/dropout settings, and hands back something you can push images through.

So the honest one-liner is: *"turn the `model:` section of the config into a model."* Analogy: the YAML is an order slip ("tiny_cnn, 16/32 channels, 128 hidden"); `build_model` is the person at the counter who reads the slip, checks the item exists on the menu (`MODELS`), and makes it.

The reason it's a separate function rather than three lines in `train.py` is that `train.py`, `evaluate.py`, `predict.py` and `visualize_layers.py` will *all* need to build the same model from the same config, and later load saved weights into it. Here's the function:

```python
def layer_table(model: TinyCNN, input_shape=(3, 32, 32)) -> list[dict]:
    model.eval()
    x = torch.zeros(1, *input_shape)
    acts = model.forward_with_activations(x)
    layers = dict(list(model.features.named_children()) + list(model.classifier.named_children()))
    rows = [dict(name="input", type="Input", out_shape=tuple(acts["input"].shape[1:]), params=0)]
    for name, t in acts.items():
        if name == "input":
            continue
        layer = layers[name]
        rows.append(dict(name=name, type=type(layer).__name__,
                         out_shape=tuple(t.shape[1:]),
                         params=sum(p.numel() for p in layer.parameters())))
    return rows
```

**The idea:** instead of calculating "16×32×32 after conv1" by hand (and getting it wrong), push a blank image through and *read* the shapes off the real tensors. Measured, not assumed. Analogy: rather than computing from the blueprint how wide each doorway is, walk a box through the house and note where it fits.

`model.eval()` — switch off training-only behaviour (dropout). Harmless here since dropout is 0, but it's the habit: anything that's not training should be in eval mode.

`x = torch.zeros(1, *input_shape)` — a fake batch of one all-black image, shape `[1, 3, 32, 32]`. The `*` unpacks the tuple into separate arguments. Zeros are fine because we only care about *shapes*, not values.

`acts = model.forward_with_activations(x)` — the recorder: returns an ordered dict `{"input": tensor, "conv1": tensor, ..., "fc2": tensor}` with every layer's output.

`layers = dict(list(model.features.named_children()) + list(model.classifier.named_children()))` — build a name → layer-object lookup. `named_children()` yields `("conv1", Conv2d(...))`, `("relu1", ReLU(...))`, … for each of the two `Sequential`s; we glue the two lists and make a dict. We need the layer objects (not just the outputs) for two things: the type name and the parameter count.

`rows = [dict(name="input", ...)]` — the first row is special-cased: it has no layer object and no params, just the input shape.

The loop — for every recorded activation except the input: look up its layer, and build one row with the name, the class name (`type(layer).__name__` → `"Conv2d"`), the output shape *without the batch axis* (`t.shape[1:]` drops the leading 1), and the parameter count (`sum(p.numel() for p in layer.parameters())` — `numel` = number of elements; a `Conv2d(3,16,3)` has a weight of 16×3×3×3 = 432 plus 16 biases = 448). ReLU and pooling have no parameters, so the sum over an empty list gives 0.

`return rows` — a list of plain dicts, so both the `__main__` printer and `visualize_layers.py` can format it however they like.

**What it assumes, and when that bites:** that the model has exactly two `Sequential`s called `features` and `classifier`. Add a `conv3` block inside `features` → works unchanged. Write a *different* model class with a different structure (say, a ResNet with named blocks) → both this and `forward_with_activations` would need to iterate differently. That's a reasonable limitation for v1; if we go to option 1 I'd keep the same two-Sequential layout precisely so these tools keep working.

**Break-it:** call `layer_table(model, input_shape=(3, 64, 64))` — the conv/pool rows adapt (64→32→16), but `fc1` crashes with a shape mismatch, because `flat_dim` was hard-coded for 32×32 input. That's the same `flat_dim` line again; it's the one brittle spot in the model.

It gets the shapes by *looking at what actually came out*, not by calculating them. It returns that as a list of rows so anything can print it.

**Analogy:** you've built a factory line with eleven stations. Instead of trusting the blueprint, you put one empty cardboard box on the conveyor and follow it. At each station you note the station's name, what the box looks like coming out (wider? smaller? flattened?), and how many adjustable dials that station has. ReLU and pooling stations have zero dials — they just reshape or filter. `fc1` has 262,272 dials, almost all of them. At the end you have a clipboard with one line per station. That clipboard is the table.

**Why it matters for you specifically:** when you add a block later, you don't recalculate anything — you send the box through again and read the new clipboard. If something's wrong (the box doesn't fit through the `fc1` door), it crashes right there and tells you which station, which is far better than discovering it on the first real training batch.

Check your understanding with one question: if you change `conv_channels` to `[16, 64]` in the YAML, which rows of the table change, and which stay the same? (Answer: `conv2`, `relu2`, `pool2`, `flatten` and `fc1` change — shapes and/or params; `conv1`, the pools' *types*, and everything after `fc1` stay the same. If that matches what you'd have guessed, you've got it.)

## Claude

This is the network itself. I'll take it in four parts: the class header and `__init__` signature, the feature extractor, the classifier, then the two forward methods.

**The class header.** `class TinyCNN(nn.Module)` — every PyTorch model inherits from `nn.Module`. That base class gives us, for free: parameter tracking (`model.parameters()` finds every weight in every sub-layer automatically), `.to(device)`, `.train()`/`.eval()` mode switching, saving and loading. The one rule it imposes is that `__init__` must call `super().__init__()` *first* — before any layers are assigned — so that the tracking machinery is set up. Forgetting that is a classic error.

**The signature.** `conv_channels=(16, 32)` — how many stencils in conv1 and conv2. `fc_hidden=128` — width of the hidden layer. `dropout=0.0`. `num_classes=10` and `in_channels=3` — CIFAR facts, with defaults so the YAML doesn't need to repeat them. `c1, c2 = conv_channels` unpacks the pair. Note: *this* is the line that ties us to two blocks. Adding a third means `c1, c2, c3 = conv_channels` and a third group of three layers.

**`self.features` — the feature extractor.** An `nn.Sequential` is a container that runs its children in order, output of one into the next. The `OrderedDict` gives them names. Six layers, in two identical patterns of conv → relu → pool:

- `nn.Conv2d(in_channels, c1, kernel_size=3, padding=1)` — the first argument is how many channels come *in* (3: R, G, B), the second how many come *out* (16). Each output channel has its own 3×3×3 stencil, so the weight tensor is `[16, 3, 3, 3]` = 432 numbers, plus one bias per output channel = 448 total. `padding=1` keeps 32×32, as discussed. Analogy: 16 different magnifying glasses, each tuned to notice one kind of local pattern.
- `nn.ReLU(inplace=True)` — zero out negatives. `inplace=True` means "overwrite the input tensor instead of allocating a new one" — saves memory, standard practice, and the cause of the recorder bug we'll get to.
- `nn.MaxPool2d(kernel_size=2)` — 2×2 windows, keep the max; stride defaults to the kernel size, so windows don't overlap and the size halves.
- `nn.Conv2d(c1, c2, ...)` — the second conv's *input* channel count must equal the first's output: 16 in, 32 out. Weight tensor `[32, 16, 3, 3]` = 4,608 + 32 biases = 4,640. Each of its 32 stencils looks at all 16 maps at once — that's how simple patterns combine into complex ones.

Why the comment says "learns WHAT is in the image": conv layers are *translation-equivariant* — a stencil that fires on a cat ear fires wherever the ear is. The feature extractor's output is "there's an ear-like thing here, fur-texture there", with rough positions.

**`flat_dim = c2 * 8 * 8`** — the bridge, and the one brittle line. After two halvings a 32×32 input is 8×8, and there are `c2` = 32 maps, so 2,048 numbers. It's computed from `c2` (so changing channel width is safe) but the `8 * 8` is hard-coded for *two pools on a 32×32 input*. Third pool → `4 * 4`; 64×64 input → `16 * 16`. The robust alternative is `nn.LazyLinear`, which measures its input size on the first forward pass, or `nn.AdaptiveAvgPool2d(1)` which collapses any spatial size to 1×1 (the "global pooling" trick used by bigger nets). For v1, the explicit number is clearer to read; the comment above it is the guard.

**`self.classifier`** — five layers, straight line:

- `nn.Flatten()` — `[32, 8, 8]` → `[2048]`. No parameters.
- `nn.Linear(flat_dim, fc_hidden)` — the fully-connected layer: a `[2048, 128]` weight matrix plus 128 biases = 262,272 parameters, 98% of the model. Every input connects to every output. This is where "there's an ear at roughly top-left and fur in the middle" gets combined into "this looks like a cat".
- `nn.ReLU` again.
- `nn.Dropout(dropout)` — with p=0 it's a pass-through; with p=0.3 it randomly zeroes 30% of the 128 values on each training step and does nothing in eval mode. A regulariser.
- `nn.Linear(fc_hidden, num_classes)` — 128 → 10. These 10 raw numbers are the logits.

Why the comment says "turns features into class scores": the classifier throws away the *where* (flatten destroys spatial layout) and keeps only the *what*. That's deliberate for classification — we don't care where the cat is.

**`forward(self, x)`** — the entire computation in one line: features, then classifier. PyTorch calls this when you write `model(x)`. You never call `forward` directly. Input `[B, 3, 32, 32]`, output `[B, 10]`.

**`forward_with_activations(self, x)`** — same path, but it keeps every intermediate. `@torch.no_grad()` tells PyTorch not to build the gradient graph, because this is for looking, not learning — faster and uses less memory. The loop walks the two `Sequential`s' children in order, applies each, and stores a **clone** of the result under the layer's name. The clone is the fix for the bug I found: without it, `acts["conv1"]` and the tensor ReLU is about to overwrite in place are the *same memory*, so after `relu1` runs, the stored conv1 output has already been zeroed. `clone()` snapshots it first. Memory cost is trivial (11 small tensors for one image).

**What I'd want you to be able to say back:** the model is two halves — `features` finds patterns and keeps rough positions; `classifier` forgets positions and decides the class. Convs change channel count, pools change size, `flat_dim` is the hinge between the halves and the first thing to update when the architecture changes.

**Break-it ideas:** set `padding=0` on conv1 and run `python -m src.model` — watch the shapes shrink and `fc1` crash; that crash message is the shape mismatch you'll learn to read. Set `conv_channels=(16, 32, 64)` in the YAML without changing the code — `c1, c2 = ...` raises "too many values to unpack", which is the error you'll see the day you add a block and forget this line.

```python
def build_optimizer(cfg, model):
    t = cfg["train"]
    if t["optimizer"] == "sgd":
        return torch.optim.SGD(model.parameters(), lr=t["lr"], momentum=..., weight_decay=..., nesterov=True)
    if t["optimizer"] == "adam":
        return torch.optim.Adam(model.parameters(), lr=t["lr"], weight_decay=...)
    raise ValueError(...)
```
The optimiser is the thing that moves the weights after each batch. `model.parameters()` hands it every learnable tensor (the 268,650 numbers). SGD with momentum: each step moves in the direction of the gradient, but keeps 90% of last step's velocity — a ball rolling downhill rather than a hiker taking independent steps; it smooths over noisy batches. `nesterov=True` is a small refinement ("look ahead before you step") that's the standard choice for CIFAR; it changes little here and could be dropped. `weight_decay` shrinks every weight slightly each step — the L2 regulariser from the config. Adam is the alternative: it adapts the step size per parameter, which makes it forgiving of a badly chosen learning rate, at the cost of slightly worse final accuracy on image models. Same registry pattern as `build_model`: unknown name → clear error.

```python
def build_scheduler(cfg, optimizer, epochs):
    s = cfg["train"].get("scheduler", "none")
    if s == "cosine": return CosineAnnealingLR(optimizer, T_max=epochs)
    if s == "step":   return StepLR(optimizer, step_size=max(1, epochs // 3), gamma=0.1)
    if s == "none":   return None
```
The scheduler changes the learning rate over time; we call `.step()` on it once per epoch. **Cosine** glides from the starting lr down to ~0 along a half-cosine curve — big steps while far from the answer, tiny steps at the end to settle into the valley. You can see it in your log's `lr` column: 0.05, 0.0495, 0.0478 … 0.0005. **Step** is the older recipe: hold, then drop 10× at fixed epochs (here every third of the run). **None** keeps lr constant — fine for a smoke test, usually a few % worse for a real run. Returning `None` for "none" means the loop has to check `if scheduler is not None`; the alternative is a do-nothing scheduler object, which is cleaner but more code.

One design note across all three: they take `cfg` and return a PyTorch object, nothing else — no side effects, trivially unit-testable, and the YAML field names appear in exactly one place each.

Block 2 of `train.py`: `run_epoch` — the engine. One function, used for both training and validation; the only difference is whether you hand it an optimiser.

```python
def run_epoch(model, loader, criterion, optimizer=None, max_batches=None):
    training = optimizer is not None
    model.train(training)
    total_loss, correct, seen = 0.0, 0, 0
    with torch.set_grad_enabled(training):
        for b, (x, y) in enumerate(loader):
            if max_batches is not None and b >= max_batches:
                break
            logits = model(x)
            loss = criterion(logits, y)
            if training:
                optimizer.zero_grad()
                loss.backward()
                optimizer.step()
            total_loss += loss.item() * len(y)
            correct += (logits.argmax(dim=1) == y).sum().item()
            seen += len(y)
    return total_loss / seen, correct / seen
```

**The idea.** An epoch is one pass over a loader, batch by batch. For each batch: push images through the model, measure how wrong it was, and — if we're training — nudge the weights to be less wrong. Count hits along the way. Return the average loss and accuracy.

Analogy: a practice exam. Training mode = the student answers a page, gets the marks back, and *adjusts* before the next page. Validation mode = same exam, but the marks are only recorded; no adjusting allowed.

Line by line:

`training = optimizer is not None` — the single switch. Pass an optimiser → train; pass `None` → evaluate. One function instead of two near-identical ones means they can't drift apart (the classic bug where the val loop computes accuracy slightly differently from the train loop).

`model.train(training)` — flips the model's mode. The only layer in TinyCNN that cares is Dropout (active in train mode, off in eval). BatchNorm would care too if we add it in option 1. Forgetting this is a very common bug: evaluating with dropout still on gives noisy, pessimistic val scores.

`with torch.set_grad_enabled(training):` — PyTorch normally records every operation so it can compute gradients later. That costs memory and time. In eval mode we don't need gradients, so we switch recording off for the whole block. Equivalent to `torch.no_grad()` when `training` is False.

`for b, (x, y) in enumerate(loader):` — the DataLoader hands out `(images [B,3,32,32], labels [B])`; `b` is the batch index. `max_batches` is the `--smoke` hook: stop after a handful so the whole script runs in seconds.

`logits = model(x)` — the forward pass: `[B, 10]` raw scores.

`loss = criterion(logits, y)` — `criterion` is `nn.CrossEntropyLoss()`. It applies softmax internally and then measures how much probability the model gave to the *correct* class, averaged over the batch: 0 if it was certain and right, large if it was certain and wrong. A random 10-class model scores ln(10) ≈ 2.303 — which is exactly what your smoke run printed at epoch 1 (`2.308`), a nice sanity check that the loss is wired correctly.

The three training lines, in strict order:
- `optimizer.zero_grad()` — clear the gradients from the previous batch. PyTorch *accumulates* gradients by default; forgetting this line means every step uses the sum of all past gradients, and training goes haywire.
- `loss.backward()` — backpropagation: compute the gradient of the loss with respect to every one of the 268,650 parameters. This is where the recorded operations are used.
- `optimizer.step()` — move each parameter a little against its gradient (scaled by lr, with momentum). The actual learning.

`total_loss += loss.item() * len(y)` — `loss` is a per-batch *mean*; multiply by the batch size to get the batch *sum*, so that the last, smaller batch (72 images) doesn't get the same weight as a full one. `.item()` turns a one-element tensor into a plain float, which also detaches it from the gradient graph (otherwise we'd be keeping the whole graph alive across the epoch — a memory leak).

`correct += (logits.argmax(dim=1) == y).sum().item()` — predicted class = index of the largest logit along the class axis; compare to truth; count the Trues.

`return total_loss / seen, correct / seen` — divide by the number of images actually processed (`seen`, not `len(loader.dataset)`, so the `--smoke` partial pass is still correct).

**Two review questions you should be able to answer now:** why can't `zero_grad` go *after* `step`? (It can, actually — as long as it's before the next `backward`. Before is the convention because it's harder to forget.) And why does the train accuracy printed per epoch tend to be slightly *lower* than val early on, as in your log? (Because train accuracy is averaged over the epoch *while the weights are still improving*, and train images are augmented — harder — while val images are clean. Train and val crossing over later is the normal signature of a model that has learned the training set well.)

**What it produces.** A Markdown document in four parts: a header with the date; a one-glance summary line of the hyperparameters that matter most (model, params, epochs, optimiser, lr, scheduler, augmentation); the *measured* layer table — a call to `layer_table`, so it reflects whatever the model actually is at that moment, not what the docstring claims; and the entire config file dumped verbatim. That last part is the safety net: even if I forgot to put some knob on the summary line, it's in the YAML block.

**Why it's split in two.** `run_card_text` builds the string and returns it; `write_run_card` just saves it. The split lets `evaluate.py` reuse the same text to append to `summary.md` without writing a second file. Rule of thumb: a function that *computes* something and a function that *does I/O* are easier to test and reuse apart than together.

**Small things worth knowing.** `'×'.join(map(str, r['out_shape']))` turns the tuple `(16, 32, 32)` into the string `16×32×32` — purely cosmetic. `{count:,}` is Python's thousands separator (`268,650`). `yaml.safe_dump(cfg, sort_keys=False)` writes the config back out *in the original order* — the default would alphabetise it, which makes the dump harder to compare to your file. `time.strftime` gives a human date; no seconds, because the card is for reading, not for sorting.

**When it runs.** `train()` calls `write_run_card` right after building the model and *before* the first epoch — so the card exists even if training crashes or you Ctrl-C it. An aborted run still leaves a record of what was attempted.

**What it doesn't record (possible v2):** the git commit hash, so you could link a card to the exact code version. Two lines with `subprocess.run(["git", "rev-parse", "--short", "HEAD"])`; I left it out to avoid a hard dependency on git being present. Worth adding once the experiments start, if you like.


Three phases per batch, and only the middle one differs between train and val:

1. **Measure** (always): forward pass, then loss. The loss is the exam mark for this batch — one number.
2. **Learn** (training only): `zero_grad` wipes the scratch paper, `backward` works out which direction each of the 268,650 weights should move to lower *this batch's* loss, `step` moves them a tiny bit. Validation skips this entirely — look but don't touch.
3. **Count** (always): add this batch's loss and hits to the running totals.

Three things that make it correct rather than roughly right:

- `model.train(training)` + `set_grad_enabled(training)` are set *once* before the loop, from the same boolean. The mode (dropout on/off) and the gradient recording (on/off) always agree with each other and with whether an optimiser was passed. One switch, three effects.
- The loss is multiplied by `len(y)` before adding, and divided by `seen` at the end — so the arithmetic is a true per-image average even though the last batch is 72 images, not 128.
- `.item()` on the loss turns the tensor into a plain number. Without it, Python would keep a reference to the whole computation graph for every batch; memory climbs all epoch.

A test of understanding: in validation mode, is `loss` still computed? Yes — we still want val *loss* for the learning curve, we just never call `backward` on it. The gradient machinery is off, so computing it is cheap.

And the sanity numbers from your own smoke run: epoch 1 train loss `2.308` ≈ ln 10 = 2.303, the loss of pure guessing among 10 classes. Accuracy `0.097` ≈ 1/10. The function is reporting exactly what an untrained model should score. If either number had been far off, something in this loop would be wrong.

## Claude

Mostly right, with one knot worth untangling: you're bundling two separate things — the *seed* and the *number of epochs* — and they affect the weights in different ways.

**The seed decides where you start.** Before training, the 268,650 weights are filled with small random numbers; the seed just picks *which* random numbers. Different seed → different starting point on the hill. That's all it does (plus the shuffle order and the augmentation draws along the way).

**The epochs decide how far you walk.** Every batch moves the weights a little downhill. Too few epochs → you stop partway down, weights "not optimal yet" — that part of your sentence is exactly right. It's called *underfitting*, and the signature is train and val loss both still falling when the run ends. Your reference run shows this mildly: at epoch 15 the curves were still dropping, so a few more epochs would likely gain a point or two.

**Where the two meet:** two runs with different seeds start from different points and walk down *slightly different* paths, so after the same number of epochs they end at slightly different accuracies — typically ±0.3–0.5% on CIFAR for a model this size. That spread is "seed variance", and it's why serious papers report mean ± std over 3–5 seeds rather than one number. With enough epochs the paths mostly converge to similar valleys; with too few, you're measuring where you *stopped* more than where the valley *is*, and seed differences look bigger.

So: seed = starting point, epochs = distance walked, learning rate = step size. "Not enough epochs" is a distance problem, and changing the seed doesn't fix it — it just gives you a different partial walk. The thing that fixes it is more epochs (or a larger lr early on, which cosine already gives you).

Analogy, since you like them: three hikers (seeds) dropped by helicopter at three random spots on a mountainside, all walking downhill for 15 minutes (epochs). Where they end up differs a bit because they started in different places — but none of them is at the bottom if 15 minutes wasn't enough. Give them 30 minutes and they all end up near the same lake.

**Inside the loop, in order:**

1. `lr = optimizer.param_groups[0]["lr"]` — read the *current* learning rate for logging, before the scheduler changes it. That's the `lr` column you can watch decaying.
2. Train epoch, then val epoch — same function, with and without the optimiser.
3. `scheduler.step()` — *after* both passes, so the lr used during the epoch is the one we logged. Stepping it before training would shift the schedule by one epoch; a classic off-by-one.
4. Log + print. `improved = va_acc > best_acc` — strictly greater, so a tie doesn't count as progress.
5. **Checkpoints.** `state` bundles four things: the weights (`state_dict`), the config that built them, the epoch, and the val accuracy. 6. **Early stopping.** `bad_epochs` counts consecutive epochs without improvement; reset to 0 on improvement; stop when it reaches `patience` (5 in the config; 0 disables). Guards against wasting an hour on a run that plateaued at epoch 20.
7. **NaN guard.** If the loss becomes infinite or NaN — almost always a too-high learning rate — stop with a message rather than training on garbage for the remaining epochs. The check is after the save so you still have the last good checkpoint.

**Return value.** A small dict with the best accuracy, the epoch it happened, and the two paths. Scripts can call `train(cfg)` and use the result (for a hyperparameter sweep, say) without parsing the printed text.

**Two design notes for the review.** Early stopping is judged on val *accuracy*, not val *loss*. They usually agree, but loss can keep improving while accuracy is flat (the model gets more confident on things it already gets right); accuracy is what we report, so it's the honest criterion.
```python
def confusion_matrix(y_true, y_pred, n_classes):
    cm = np.zeros((n_classes, n_classes), dtype=np.int64)
    np.add.at(cm, (y_true, y_pred), 1)
    return cm
```
A grid where row = true class, column = predicted class, and each cell counts how many images landed there. `np.add.at(cm, (rows, cols), 1)` is "for each (true, pred) pair, add 1 to that cell" in one vectorised call — the loop version would be `for t, p in zip(y_true, y_pred): cm[t, p] += 1`. For the example:

```
            pred 0  pred 1  pred 2
true 0        1       1       0      ← one 0 was right, one was called a 1
true 1        0       2       0      ← both 1s right
true 2        1       0       1      ← one 2 was called a 0
```
Diagonal = correct. Everything off-diagonal is a specific kind of mistake, which is why this is the single most useful evaluation picture: it doesn't just say "wrong", it says *wrong how*.

```python
def accuracy(y_true, y_pred):
    return float((y_true == y_pred).mean())
```
Fraction of matches: 4 of 6 = 0.667. Equivalently the diagonal sum over the total.

```python
def per_class_metrics(cm):
    tp = np.diag(cm)                 # correct per class       [1, 2, 1]
    support = cm.sum(axis=1)         # how many truly each     [2, 2, 2]
    predicted = cm.sum(axis=0)       # how many predicted each [2, 3, 1]
    recall = tp / support
    precision = tp / predicted
    f1 = 2 * precision * recall / (precision + recall)
```
Three questions per class, read straight off the matrix:
- **Recall** (= per-class accuracy): *of the real class-1 images, how many did we catch?* Row-wise. Class 1: 2/2 = 1.0. Class 0: 1/2 = 0.5.
- **Precision**: *of the images we called class 1, how many really were?* Column-wise. Class 1: 2/3 = 0.667 (we over-called it once). Class 2: 1/1 = 1.0.
- **F1**: the harmonic mean of the two, one number that punishes being bad at either. Class 1: 2·(0.667·1)/(0.667+1) = 0.8.

The `np.divide(..., where=support > 0)` wrapping in the real code is the zero-safety: a class the model never predicts has `predicted = 0`, and plain division would give NaN and poison every average downstream. The test `test_per_class_metrics_zero_safe` checks exactly that case.

Why both precision and recall rather than just accuracy: a model that calls *everything* "cat" has 100% cat recall and terrible cat precision. On your reference run, cat has recall 57% and precision 62% — it both misses cats (calls them dogs) and over-calls cats (on dogs). The confusion matrix's 99 and 75 in the cat/dog cells are those two numbers in raw form.

```python
def top_k_accuracy(probs, y_true, k=2):
    topk = np.argsort(-probs, axis=1)[:, :k]
    return float((topk == y_true[:, None]).any(axis=1).mean())
```
Was the true class among the k highest-scoring? `argsort(-probs)` sorts descending (numpy only sorts ascending, hence the minus); `[:, :k]` keeps the first k columns; `y_true[:, None]` reshapes `[N]` to `[N, 1]` so it broadcasts against `[N, k]`; `.any(axis=1)` asks "a match in any of the k slots?". Your 89.9% top-2 vs 76.9% top-1 says: in 13% of cases the right answer was the runner-up — mostly the cat/dog coin-flips.

```python
def calibration_bins(probs, y_true, n_bins=10):
```
Groups predictions by their confidence (max probability) into 10 bins — 0–10%, 10–20%, … — and for each bin compares *mean confidence* to *actual accuracy*. A perfectly calibrated model's 70%-confident predictions are right 70% of the time. **ECE** (expected calibration error) is the count-weighted average gap between the two; 0 is perfect. Your model's 0.015 is very good — slightly under-confident, which is the safe direction. This matters for `predict.py` later: if we show a user "92% dog", that number should mean something.

```python
def load_image(path: Path) -> Image.Image:
    img = Image.open(path)
    img = ImageOps.exif_transpose(img)
```

Three jobs. `Image.open` reads any format PIL knows (JPEG, PNG, WebP…). `exif_transpose` is the phone fix: phones often store the pixels sideways and add a tag saying "rotate me 90° when you display this" — viewers obey the tag, numpy doesn't, so without this line a portrait photo would reach the model lying on its side. `convert("RGB")` normalises the colour mode: PNG with transparency (RGBA) drops the alpha, greyscale (L) gets replicated into three identical channels, palette images get expanded. After this line every image is three channels, whatever it started as — which is what `test_load_image_converts_modes` and `..._applies_exif_rotation` check.

```python
def to_cifar_size(img, size=32):
    w, h = img.size
    s = min(w, h)
    left, top = (w - s) // 2, (h - s) // 2
    return img.crop((left, top, left + s, top + s)).resize((size, size), Image.LANCZOS)
```
Two steps: **centre-crop to a square**, then **shrink**. The square side is the shorter dimension; the crop box is offset so it sits in the middle. For your 2160×3840 photo that's a 2160×2160 square from the vertical middle — which is exactly why the litter tray dominated: the middle of a tall photo was the tray, not the cat. The alternative — squash the whole photo to 32×32 without cropping — keeps everything but distorts shapes (a tall photo becomes a wide-eyed version of itself); for a classifier trained on natural proportions, cropping is the lesser evil. `LANCZOS` is the high-quality resampling filter: when shrinking 2160 → 32 (67× smaller), each output pixel averages ~4,500 input pixels, and a cheap filter would alias badly. The test `test_to_cifar_size_crops_centre_square` builds a 300×100 red/green/blue stripe image and checks the centre pixel of the result is green.

```python
def to_model_tensor(small, eval_tf):
    arr = np.array(small, dtype=np.uint8)          # [32,32,3]
    chw = torch.from_numpy(arr).permute(2, 0, 1)   # [3,32,32] uint8
    return eval_tf(chw).unsqueeze(0)               # [1,3,32,32] float, normalised
```
From here on it's *identical* to what the validation set goes through, and that's the whole point. HWC → CHW is the same permute as in `CIFAR10Arrays.__getitem__`; `eval_tf` is the same transform `build_transforms` gives the val loader (to-float + mean/std normalise, no augmentation); `unsqueeze(0)` adds the batch axis because the model expects `[B, 3, 32, 32]` even for B = 1. If any of these differed from the training pipeline — say, forgetting normalisation — the model would see inputs from a different distribution and quietly produce garbage with high confidence. `test_to_model_tensor_shape_and_normalisation` checks the shape and that a white image maps *above* 1.0 (proof the normalisation ran; un-normalised would cap at 1.0).

**One design note:** `eval_tf` comes from the checkpoint's own config (`build_transforms(cfg)` in `predict()`), not from `baseline.yaml` on disk. So if you later train an experiment with `normalize: false`, predicting with that checkpoint automatically skips normalisation too. The checkpoint carries its own pre-processing contract.

**Break-it:** feed a 1×1 pixel image — works, becomes a flat 32×32 colour. Feed a 10000×10 banner — the centre crop is a 10×10 square from the middle, so most of it is thrown away; that's the crop policy's known weakness, and the contact sheet's middle column is how you'd notice.

Before you remove it, one thing to check in your reasoning: the function does two jobs, and only one of them is the problem.

- **Crop to square** — this is the part that bit you (it picked the tray, not the cat).
- **Resize to 32×32** — this is non-negotiable. The model's `fc1` expects exactly 2,048 inputs = 32·8·8; feed it anything else and it crashes. Some resize must happen somewhere.

And here's the thing: if you crop by hand first, the auto-crop becomes a *no-op*. On a square image `s = min(w, h) = w`, `left = top = 0`, and the crop box is the whole image. Your `cat_tight_crop.jpg` went through this exact function unchanged — only the resize did anything. So your workflow (crop manually, then feed) already works with the code as is, and removing the function wouldn't change the result for square inputs; it would just break non-square ones.

What *would* be a real design choice is what to do with a non-square image you *haven't* pre-cropped. Three options:

1. **Centre-crop** (current): keeps proportions, may lose the subject if it's off-centre. Failure is visible in the contact sheet.
2. **Squash** (resize whole image to 32×32, no crop): keeps everything, distorts proportions — a tall photo's cat becomes a short fat cat. Models trained on natural proportions generally dislike this, but nothing is lost.
3. **Refuse**: raise an error if the image isn't square, forcing manual cropping. Most honest, least convenient.

My suggestion: keep the function, add a `--crop {center,squash,none}` flag defaulting to `center`, where `none` raises a clear error for non-square inputs. Then your manual-crop workflow is option 3 with a safety net, and you can compare 1 vs 2 on the same photo as another cheap experiment ("does squashing hurt?"). It's about eight lines; say the word and I'll add it with a test.

The general lesson, worth writing down: automatic pre-processing isn't wrong, it's *opinionated*, and the opinion ("the subject is in the middle") should be visible and overridable — which is why the contact sheet shows the 32×32 the model saw.
