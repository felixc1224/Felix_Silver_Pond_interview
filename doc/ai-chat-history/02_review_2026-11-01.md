Think of `check_counts` as a stock-take. Someone handed us three boxes (train, val, test) and a label list; we count what's in each box and refuse to continue if the numbers aren't what we ordered.

Line by line:

`def check_counts(d):` — `d` is the big dictionary that `build_dataloaders()` returned. It holds the three datasets under `d["train"]`, `d["val"]`, `d["test"]`, plus `d["class_names"]`.

`names = d["class_names"]` — the list of 10 strings, `['airplane', 'automobile', ...]`. Position in the list = label number, so `names[5]` is `'dog'`.

`print(f"classes ({len(names)}): {names}")` — just shows that list and how long it is, so you can eyeball "10 classes, right names".

`for split in ("train", "val", "test"):` — do the same thing three times, once per box.

`counts = Counter(d[split].labels.tolist())` — `d[split].labels` is the numpy array of label numbers for that box (e.g. 45,000 numbers between 0 and 9). `.tolist()` turns it into a plain Python list. `Counter` tallies it: you get something like `{0: 4500, 1: 4500, ..., 9: 4500}` — "how many of each label". Analogy: tipping out a bag of coloured marbles and counting each colour.

`per_class = [counts[c] for c in range(len(names))]` — rewrite that tally as a list in label order 0→9, so it prints as `[4500, 4500, ...]`. Why not just print `counts`? A dict prints in whatever order it was filled, which would be confusing; a list in class order is easy to read, and it also guarantees a missing class shows as `0` rather than silently not appearing.

`print(f"{split:5s}: {len(d[split]):6d} images | per class: {per_class}")` — one line per box. The `:5s` and `:6d` are just padding so the three lines line up in columns.

`assert len(d["train"]) == 45_000 and len(d["val"]) == 5_000 and len(d["test"]) == 10_000` — the first hard rule: the box sizes must be exactly what we planned. `45_000` is just `45000` with an underscore for readability. If any size is off, `assert` stops the program with an `AssertionError` right there — a loud failure, which is what we want in a check script.

`assert all(v == 500 for v in Counter(d["val"].labels.tolist()).values()), "val not stratified"` — the second hard rule, and the one that proves the split is stratified: count the val labels again, take just the numbers (`.values()`), and demand that every single one is 500. `all(...)` is True only if every item passes. The string after the comma is the message you'd see if it fails. Note this only checks val, not train — train's 4,500-each follows automatically if val is 500-each and the totals are 5,000 per class.

`print("OK counts")` — only reached if both asserts passed.

Two things worth noticing for your review: the numbers 45,000 / 5,000 / 500 are hard-coded here, so if we ever change `val_per_class` in the loader this test will fail even though nothing is wrong — that's the "too strict?" question in the guide. And `assert` is the simplest way to write a check, but Python can skip asserts when run with `python -O`; for a verification script that's fine, for real tests we'll use pytest later.

def check_no_overlap(d):

    assert train_set | val_set == set(range(50_000)), "train+val do not cover all 50k"
    print(f"split CSVs: {SPLIT_DIR / 'train_idx.csv'} , {SPLIT_DIR / 'val_idx.csv'}")
    print("OK no overlap, full coverage")
```

## Claude

This one checks that the split is a clean cut: every one of the 50,000 original images went to *exactly one* of train or val — none to both, none to neither.

Analogy: you deal a 50,000-card deck into two piles. Two things can go wrong: the same card ends up in both piles (impossible with a real deck, very possible with a software bug — you'd be testing on cards you also practised on, which is cheating without knowing it), or some cards fall on the floor and are in neither pile. This function checks both.

Line by line:

`train_set, val_set = set(d["train_idx"].tolist()), set(d["val_idx"].tolist())` — `d["train_idx"]` and `d["val_idx"]` are the two index arrays from the split (45,000 and 5,000 numbers in the range 0–49,999, i.e. *positions in the original 50k array*). `.tolist()` makes plain lists, `set(...)` makes Python sets. A set is a bag with no duplicates and no order, and it's the natural tool for "what's in A and also in B" questions.

`overlap = train_set & val_set` — `&` on sets is *intersection*: the elements present in both. We want this to be empty. Picture a Venn diagram; `&` is the lens-shaped middle.

`print(...)` — show the three sizes. A healthy run prints `45000, 5000, 0`.

`assert not overlap, f"LEAK: ..."` — an empty set counts as `False` in Python, so `not overlap` is `True` only when nothing is shared. If something *is* shared, the program stops and the message says how many. I called it a LEAK because that's the ML term: validation data leaking into training makes your val accuracy a lie — you'd be grading the student on questions they memorised.

`assert train_set | val_set == set(range(50_000)), ...` — `|` on sets is *union*: everything in either. `set(range(50_000))` is `{0, 1, 2, ..., 49999}`. So this says: train and val together must be exactly the full set of positions. This catches cards on the floor (an index missing from both) and also a wrong index (e.g. 50,000 or −1 sneaking in, which would make the union not equal).

Why both asserts? The first alone would pass if val were empty. The second alone would pass if every index were in *both* sets. Together they pin it down: a true partition.

`print(f"split CSVs: ...")` — reminds you where the split lives on disk, so you know which files to open or md5.

`print("OK no overlap, full coverage")` — reached only if both rules passed.

One subtlety worth knowing: this checks the *indices* that `dataset.py` is using in memory, which it read back from the CSVs. So it also indirectly checks the CSVs — that's why the "break it" experiment in the guide (edit a row of `val_idx.csv` to duplicate a train index) will make the first assert fire.

def check_batch_shapes(d):
    for split in ("train", "val", "test"):
        x, y = next(iter(d[f"{split}_loader"]))
        print(f"{split:5s} batch: x {tuple(x.shape)} {x.dtype} range [{x.min():.3f}, {x.max():.3f}] | y {tuple(y.shape)} {y.dtype}")
        assert x.shape[1:] == (3, 32, 32) and x.dtype.is_floating_point
        assert 0.0 <= x.min() and x.max() <= 1.0, "expected [0,1] pixel range with no transform"
    print("OK batch shapes")

```

## Claude

This is the first function that looks at the data *the way the model will see it*. The two before it checked bookkeeping (counts, indices); this one actually pulls a real batch out of each DataLoader and checks it's the right shape, the right number type, and the right value range. If the model is a machine with a specific slot, this checks the parts we're feeding it fit the slot.

Line by line:

`for split in ("train", "val", "test"):` — once per loader.

`x, y = next(iter(d[f"{split}_loader"]))` — three things packed in one line:
- `d[f"{split}_loader"]` builds the key `"train_loader"` etc. and fetches the DataLoader (the renamed keys from the bug I hit).
- A DataLoader isn't a list — you can't do `loader[0]`. It's something you *iterate over*, handing out one batch at a time. `iter(...)` starts that iteration; `next(...)` takes the first batch and stops. Analogy: a vending machine that only dispenses in order — `iter` is putting the coin in, `next` is pressing the button once.
- A batch comes out as a pair: `x` the images, `y` the labels. The DataLoader collected 128 single `(image, label)` items from `__getitem__` and stacked them.

`print(...)` — shows the shape, dtype and min/max of `x`, and shape/dtype of `y`. You saw: `x (128, 3, 32, 32) torch.float32 range [0.000, 1.000] | y (128,) torch.int64`.

`assert x.shape[1:] == (3, 32, 32) and x.dtype.is_floating_point` — `x.shape` is `(128, 3, 32, 32)`: batch size, colour channels, height, width. `shape[1:]` drops the first number because the batch size isn't a property of the data — the last batch of an epoch can be smaller (45,000 ÷ 128 leaves a remainder of 72). So we only insist on the per-image part: 3 channels × 32 × 32. The second half checks the pixels are floats, not the original uint8 integers — neural nets do arithmetic in floating point, and feeding uint8 would either crash or silently behave badly.

`assert 0.0 <= x.min() and x.max() <= 1.0, "expected [0,1] pixel range with no transform"` — pixels started as 0–255; `__getitem__` divided by 255, so they must now sit between 0 and 1. If someone forgot the division (max would be 255) or divided twice (max ≈ 0.004), this trips. The message is deliberately honest: this rule is only true *with no transform*. Once we add normalisation with `CIFAR10_MEAN/STD` the values will become roughly −2 to +2, and this assert will fail on purpose — it's the item flagged in the review guide, and we'll update the test when we get there rather than loosen it now.

`y` isn't asserted, only printed — a small gap. A stricter version would check `y.dtype == torch.int64` (what PyTorch's loss function expects) and `0 <= y.min()` and `y.max() <= 9`. Worth noting as a v2 improvement.

`print("OK batch shapes")` — all three loaders passed.

One thing this does *not* check: that the shuffle works (train batch order changes between runs) or that `x` and `y` are still paired correctly after batching. The second one is what the picture grid is for — if the labels under the images are right, the pairing survived.

This is the "fold the flat-packed image back into a photo" step, and it's the function most worth drawing, so let me do that.

**What's in a batch file.** Each `data_batch_N` is a Python dictionary that was frozen to disk with `pickle`. The two keys we care about: `d["data"]`, a table of 10,000 rows × 3,072 numbers, and `d["labels"]`, a list of 10,000 integers 0–9. One row = one image, laid out flat like this:

```
row i:  [ r r r r ... r | g g g g ... g | b b b b ... b ]
          1024 reds       1024 greens     1024 blues
          (= 32×32)       (= 32×32)       (= 32×32)
```

The authors stored each colour channel as one long strip, row by row. To get a picture back we have to cut the strips and stack them.

Line by line:

`def _read_batch(path: Path) -> tuple[np.ndarray, np.ndarray]:` — takes one file path, returns two arrays. The leading underscore is a Python convention for "internal helper — meant to be called by `load_cifar10`, not by outside code".

`with open(path, "rb") as f:` — open in *read-binary* mode. Pickles are bytes, not text; `"r"` alone would try to decode them as text and fail.

`d = pickle.load(f, encoding="latin1")` — unfreeze the dictionary. `encoding="latin1"` is a historical wart: these files were pickled with Python 2 in 2009, and Python 3 needs to be told how to interpret the old byte strings; latin1 is the setting that maps them 1-to-1 without error. Without it you get `UnicodeDecodeError`. (This is also why the keys come back as `"data"` and not `b"data"`.)

`images = d["data"].reshape(-1, 3, 32, 32).transpose(0, 2, 3, 1)` — the heart of it, in two moves:

- `.reshape(-1, 3, 32, 32)`: cut each 3,072-strip into 3 channels × 32 rows × 32 columns. Reshape doesn't move any numbers — it just changes how numpy *reads* the same memory. The `-1` means "you work out this dimension": numpy knows the total is 10,000 × 3,072 and the other three dims multiply to 3,072, so `-1` becomes 10,000. It lets the same line work for any batch size. Result: `[N, 3, 32, 32]`, i.e. *channels first*.

- `.transpose(0, 2, 3, 1)`: reorder the axes. Read the numbers as "the new axis k is the old axis listed at position k":

  ```
  old:  axis0=N   axis1=C   axis2=H   axis3=W
  new:  (0, 2, 3, 1)  →  N, H, W, C
  ```

  So we go from `[N, 3, 32, 32]` (channels first, PyTorch style) to `[N, 32, 32, 3]` (channels last, photo style — the way matplotlib, PIL and your eyes expect). Transpose, like reshape, doesn't copy data; it changes the reading order.

Why land on channels-last here, when PyTorch wants channels-first? Because this array is our *storage* format — it's what `show_random_samples` would draw from, what a PNG export would use, and what any image library understands. The flip to channels-first happens per-image inside `__getitem__`, right before the model. Storage in the human convention, conversion at the model's door.

`labels = np.asarray(d["labels"], dtype=np.int64)` — the labels come out of the pickle as a plain Python list; turn it into a numpy array of 64-bit integers. `int64` specifically because that's what PyTorch's `CrossEntropyLoss` demands for class targets — picking it here means no surprises later.

`return images, labels` — the pair, positions aligned: `images[i]` goes with `labels[i]`. That alignment is the thing the sample grid implicitly tests.

The "break it" experiment from the guide is worth actually doing once: delete the `.transpose(...)` and run `verify_data.py`. All the automatic checks will still pass (shapes get fixed up downstream), but the grid will show scrambled stripes — a concrete demonstration of why the human check exists.

def make_stratified_split(labels: np.ndarray, val_per_class: int = 500,
                          seed: int = 42) -> tuple[np.ndarray, np.ndarray]:
    """
    For each class, shuffle its indices with a seeded RNG and take `val_per_class`
    for validation; the rest go to training. 10 classes x 500 = 5000 val images.
    """
    rng = np.random.default_rng(seed)
    train_idx, val_idx = [], []
    for c in np.unique(labels):
        idx = np.flatnonzero(labels == c)      # all positions where label == c
        rng.shuffle(idx)
        val_idx.append(idx[:val_per_class])
        train_idx.append(idx[val_per_class:])
    train_idx = np.sort(np.concatenate(train_idx))
    val_idx = np.sort(np.concatenate(val_idx))
    return train_idx, val_idx
```

## Claude

This is the most important function in the file — it's the one that decides which 5,000 images we're allowed to grade ourselves on. Everything else is plumbing; this is a decision. Worth going slowly.

**The idea first.** We have 50,000 labelled images, 5,000 per class. We want a validation set that (a) is a fair sample of every class, (b) is chosen randomly so there's no hidden bias, and (c) is the *same* every time anyone runs the code. The function handles each: (a) by working one class at a time, (b) with a shuffle, (c) with a seed.

Analogy: ten jars of marbles, 5,000 each, one colour per jar. For each jar: shake it, scoop out 500 without looking, put them in the "val" bowl, pour the remaining 4,500 into the "train" bowl. Shaking with a fixed seed means the same marbles come out every time.

Line by line:

`def make_stratified_split(labels, val_per_class=500, seed=42):` — input is just the label array (50,000 numbers). It doesn't need the images at all, because it only decides *positions*. Output is two arrays of positions. `val_per_class` and `seed` are parameters with defaults so the policy is visible and changeable in one place.

`rng = np.random.default_rng(seed)` — a private random-number generator seeded with 42. "Private" matters: the older style `np.random.seed(42)` sets a *global* state, so any other code that draws random numbers would shift our split. `default_rng` gives us our own dice that nobody else touches. 42 itself is arbitrary (a programmer in-joke); any fixed integer works, what matters is that it's fixed.

`train_idx, val_idx = [], []` — two empty lists that will collect one chunk per class.

`for c in np.unique(labels):` — `np.unique` returns the sorted distinct values: `[0, 1, 2, ..., 9]`. So the loop runs ten times, once per class. Using `unique` rather than `range(10)` means the function would also work for a dataset with 7 or 43 classes.

`idx = np.flatnonzero(labels == c)` — `labels == c` makes a 50,000-long array of True/False ("is this image a cat?"). `flatnonzero` returns the *positions* of the Trues. For `c = 3` that's 5,000 positions somewhere in 0–49,999, in increasing order. This is the "contents of one jar".

`rng.shuffle(idx)` — shake the jar. Shuffles the positions in place, using our seeded generator. Because the generator state advances with each call, class 0 gets one shuffle, class 1 the next, and so on — deterministic across runs, different across classes.

`val_idx.append(idx[:val_per_class])` — scoop the first 500 of the shuffled positions into val. Since they're shuffled, "first 500" is a random 500.

`train_idx.append(idx[val_per_class:])` — everything from position 500 onward (4,500 of them) goes to train. The two slices `[:500]` and `[500:]` are complementary by construction — that's where "no overlap, full coverage" actually comes from; `check_no_overlap` just confirms it.

`train_idx = np.sort(np.concatenate(train_idx))` — after the loop we have ten chunks of 4,500; glue them into one array of 45,000, then sort. Sorting is cosmetic: it makes the CSV readable (positions ascending) and the result independent of class order. It doesn't undo the randomness — *which* positions are in the set was decided by the shuffle; sorting only changes the order we list them in. Shuffling for training happens later, in the DataLoader, every epoch.

`val_idx = np.sort(np.concatenate(val_idx))` — same for the ten chunks of 500 → 5,000.

`return train_idx, val_idx` — two position arrays. The caller uses them as `x_train[train_idx]`.

**The alternatives I considered.** `sklearn.model_selection.train_test_split(indices, test_size=5000, stratify=labels, random_state=42)` does this in one line and is what most people reach for. I didn't use it because it adds scikit-learn as a dependency for a single call, and because this ten-line version shows the mechanism — which is the point of this project. A non-stratified version (`rng.permutation(50000)` and take the first 5,000) is even shorter, but val would end up with roughly 500 ± 20 per class instead of exactly 500; on balanced CIFAR-10 that would barely matter, but on an imbalanced dataset it can leave a rare class almost absent from val, and the habit is worth building.

**Edge cases for the "break it" experiments.** Same seed twice → identical arrays (try `np.array_equal`). Seed 43 → different arrays. `val_per_class=6000` on a class with 5,000 → `idx[:6000]` just takes all 5,000 and `idx[6000:]` is empty, so val gets everything and train gets nothing for that class, silently. That's the weakness: there's no check that `val_per_class` is less than the class size. A one-line `assert val_per_class < len(idx)` inside the loop would close it — worth adding in v2.

    __getitem__ returns (image tensor [3,32,32] float32, label int).
    `transform` is an optional torchvision transform applied to a uint8 CHW tensor.
    """

    def __init__(self, images: np.ndarray, labels: np.ndarray, transform=None):
        assert len(images) == len(labels), "images and labels must align"
        self.images = images          # uint8 [N,32,32,3]
        self.labels = labels          # int64 [N]
        self.transform = transform

    def __len__(self) -> int:
        return len(self.labels)

    def __getitem__(self, i: int):
        # HWC uint8 numpy -> CHW uint8 tensor (what torchvision transforms expect)
        img = torch.from_numpy(self.images[i]).permute(2, 0, 1)
        if self.transform is not None:
            img = self.transform(img)
        else:
            img = img.float() / 255.0  # plain [0,1] scaling if no transform given
        return img, int(self.labels[i])

```

## Claude

This is the bridge between "numpy arrays sitting in memory" and "things PyTorch can feed to a model". It's the direct replacement for `ImageFolder` in your GTSRB assignment, so it's worth comparing to that as we go.

**The contract first.** PyTorch's `Dataset` is an abstract idea: "a thing you can ask *how long are you?* and *give me item number i*." That's all a DataLoader needs — it will call `len()` once to know how many items there are, then call `__getitem__` with random (or sequential) numbers and stack the answers into batches. `ImageFolder` fulfils that contract by scanning folders of PNGs; our class fulfils it by indexing arrays. The DataLoader can't tell the difference, which is why the rest of your assignment-style code works unchanged.

Analogy: a Dataset is a librarian. The DataLoader doesn't care whether the books are on shelves (PNG files) or in a warehouse crate (numpy array) — it just asks "how many books?" and "hand me book 17".

Line by line:

`class CIFAR10Arrays(Dataset):` — the `(Dataset)` means we inherit from PyTorch's base class, which is what makes DataLoader accept it.

`def __init__(self, images, labels, transform=None):` — the constructor. We hand it the arrays for one split (e.g. 45,000 train images and their labels) and an optional transform.

`assert len(images) == len(labels), "images and labels must align"` — a cheap guard against the classic bug of passing `x_train` with `y_val`. If the counts differ, fail loudly at construction rather than mysteriously mid-training.

`self.images = images` / `self.labels = labels` / `self.transform = transform` — store them. No copying, no conversion: the arrays stay uint8 HWC exactly as `load_cifar10` produced them. Memory stays at ~150 MB.

`def __len__(self): return len(self.labels)` — "how many books". The DataLoader uses this to know when an epoch ends.

`def __getitem__(self, i):` — "hand me book i". This runs once per image, 45,000 times per epoch, so it should be cheap — and it is: one slice, one permute, one divide.

`img = torch.from_numpy(self.images[i]).permute(2, 0, 1)` — two moves. `self.images[i]` picks one `[32, 32, 3]` uint8 image; `torch.from_numpy` wraps it as a tensor *without copying* (it shares memory with the numpy array). Then `permute(2, 0, 1)` reorders HWC → CHW: new axis 0 = old axis 2 (colour), new 1 = old 0 (height), new 2 = old 1 (width). This is the flip I mentioned in `_read_batch`: storage is human-order, the model gets PyTorch-order, and the conversion happens here at the door. PyTorch wants channels first because its convolution kernels are laid out that way.

`if self.transform is not None: img = self.transform(img)` — if a torchvision transform pipeline was supplied (later: random crop, horizontal flip, normalise), apply it to the uint8 CHW tensor. The transform is then responsible for converting to float and scaling. This is where data augmentation will plug in without touching anything else in the class.

`else: img = img.float() / 255.0` — no transform supplied (today's case): convert uint8 → float32 and scale 0–255 → 0–1. This is why `check_batch_shapes` currently sees `[0, 1]`, and why that assert will need updating once a normalising transform takes over this job.

`return img, int(self.labels[i])` — the pair. `int(...)`

## Claude

This is the assembly line: it calls the pieces you've already reviewed in order — load, split, wrap — and returns one dictionary. No new mechanism; the value is in *which arguments go where*.

`data = load_cifar10()` — everything into memory (50k train, 10k test, class names).

`train_idx, val_idx = get_or_create_split(data["y_train"], data["class_names"], val_per_class, seed)` — get the frozen split (from the CSVs, or create them the first time). Only the labels are passed, because the split needs positions, not pixels.

The `return dict(...)` builds six entries:

`train=CIFAR10Arrays(data["x_train"][train_idx], data["y_train"][train_idx], train_transform)` — `x_train[train_idx]` is numpy *fancy indexing*: hand it an array of 45,000 positions and it returns a new array with exactly those rows, in that order. Same for the labels, with the *same* positions, so image i and label i stay paired. Wrapped as a Dataset with the **training** transform.

`val=CIFAR10Arrays(data["x_train"][val_idx], data["y_train"][val_idx], eval_transform)` — the other 5,000 positions out of the same source array, wrapped with the **eval** transform.

`test=CIFAR10Arrays(data["x_test"], data["y_test"], eval_transform)` — the 10k test set, no indexing needed, also **eval** transform.

`class_names=...`, `train_idx=...`, `val_idx=...` — passed through so downstream code (the verify script, later the confusion matrix) can use them without reloading.

**The one design decision in here: two transform slots, not one.** Train gets `train_transform`; val and test both get `eval_transform`. When we add augmentation — random crops, horizontal flips — it goes only in `train_transform`. Val and test must see the images exactly as they are, because they're measuring how well the model handles real, unaltered inputs; augmenting them would make the score noisy and non-reproducible. Normalisation (mean/std), by contrast, goes in *both*, because the model expects it at all times. Analogy: in training you practise with the ball wet, in the dark, with a strong wind — in the exam the conditions are standard. Today both slots are `None`, so all three behave identically (plain /255), but the plumbing is already in place.

**Memory note for the review:** fancy indexing copies. `x_train[train_idx]` makes a new 138 MB array, `x_train[val_idx]` a 15 MB one, and the original 154 MB `x_train` is still alive while this function runs — so peak is briefly ~300 MB plus the 31 MB test set. After the function returns, `data` goes out of scope and the original can be garbage-collected. On an 8 GB laptop this is nothing; on a Raspberry Pi you'd index lazily inside `__getitem__` instead. Worth knowing the trade-off, not worth changing.

**Still unenforced:** the test set is built here and could be iterated at any time. The "sealed until the end" rule remains discipline, as noted earlier.

Yes — this is the final product, the thing every other file will call. It takes the three Datasets and wraps each in a DataLoader, which is the part that turns "give me item i" into "give me the next batch of 128". Small function, but every argument is a decision.

`def build_dataloaders(batch_size=128, num_workers=0, **kwargs):` — the two loader settings are explicit; `**kwargs` means "any other keyword arguments, pass them straight through". So `build_dataloaders(batch_size=64, seed=7)` sends `seed=7` down to `build_datasets`. It keeps this function from having to repeat every parameter of the one below it.

`ds = build_datasets(**kwargs)` — the dictionary from the previous function.

The three `DataLoader(...)` calls — a DataLoader is the batching machine. Each epoch it decides an order of indices, calls `__getitem__` for each, and stacks every 128 results into one `[128, 3, 32, 32]` tensor plus one `[128]` label tensor. The arguments:

- `batch_size=128` — how many images per step. Bigger batches = fewer steps per epoch and smoother gradient estimates, but more memory and, past a point, worse generalisation. 128 is a common CIFAR-10 default and comfortable on CPU; we'll likely tune it in the config later. With 45,000 images that's 351 full batches plus one of 72 — the DataLoader keeps that last partial batch by default (`drop_last=False`), which is fine for us.
- `shuffle=True` for train, `False` for val and test — the one asymmetry. Shuffling train each epoch means the model never sees the same sequence twice, so it can't learn "a truck always follows a cat"; it also means batches are a fair mix of classes rather than runs of one class. For val and test, order doesn't affect the score, and a fixed order makes results reproducible and lets us line up predictions with indices for the confusion matrix later.
- `num_workers=0` — the comment in the docstring is the decision. Workers are extra processes that prepare batches in parallel; they're a big win when `__getitem__` is slow (decoding JPEGs from disk). Ours is a slice and a divide on in-memory arrays, so workers would spend more time shipping data between processes than they save — and on WSL, multiprocessing with large shared arrays is a known source of hangs and "too many open files" errors. Zero means everything happens in the main process: simple, debuggable, and fast enough here. If we later move to PNG-on-disk or a GPU box, this is the first knob to turn.

`return {**ds, **loaders}` — merge both dictionaries into one. This is the line that bit me: originally both dicts used the keys `train`/`val`/`test`, so the second one silently overwrote the first and the Datasets vanished. The fix was the `_loader` suffix; now the result has nine entries — three Datasets, three loaders, class names, and the two index arrays — and the verify script uses `d["train"]` for counts and `d["train_loader"]` for batches. A dict merge doesn't warn on key collisions, which is worth remembering as a general Python hazard.

**Alternatives for the review:** `pin_memory=True` and `persistent_workers=True` are the usual extra DataLoader knobs, but both only matter with GPUs or workers, so neither applies. And a sanity check you can do right now in a Python shell: `len(d["train_loader"])` should print 352 (= ceil(45000/128)).
